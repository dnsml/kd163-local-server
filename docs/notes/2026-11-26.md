## 6. 30 包尾部块长写错（腰带 / 护腕 / 护符显示空）+ 背包 60 格上限

### 6.1 症状

服务端 `30` 说已穿 9 件，客户端腰带、护腕、护符三格却是空的；背包里的东西也「有件数、看不到」。

### 6.2 30 尾部块长（真正的根因）

真服固定尾部 = 第 12 块 4B + 翅膀块 **20B** + 坐骑块 **6B**，长度与「有没有翅膀/坐骑」无关。

| 情形 | 旧实现 | 真服 | 后果 |
|---|---|---|---|
| 11 件全满 | 90B | 96B | 客户端从翅膀块开始错位解析，腰带/护腕/护符读成空 |
| 11 件全空 | 68B | 74B | 同上 |

修法（`build_30()`）：

```python
out += _enc30(_wing) + b"\x00" * 15 if wing else b"\x00" * 20   # 翅膀固定 20B
out += b"\xcd" + iid + b"\x0d\x01\x01" if mount else b"\x00" * 6 # 坐骑固定 6B
```

`work/test_acc_equip.py` 长度断言同步 +6B：第一枚戒指 90B、第二枚 92B、满配 96B、
819 卸戒指 94B、卸护符 92B、37 卸槽 1 90B。

## 7. 登录后面板属性显示成「没穿装备」（13:00 修复并实测通过）

### 7.1 现象
重登后四首饰、武器都在（`17` 里装备齐全），但角色面板显示
气血 1271 / 攻击 151-185，穿脱一次任意装备才恢复正常。

### 7.2 根因
登录回放序列里**没有 `29`**（动态属性面板）。客户端只能拿 `17` 的基础值自己算，
而 `42`（打开角色面板）回的真服原包 `43` 里带的是旧属性块，会把面板再刷回基础值。

### 7.3 修法
`cmd=42` 的回包顺序固定为 **`818 → 43 → 29 → 30`**，`43` 之后必须补一条动态 `29`：

```python
_b29role = build_29()
if _b29role:
    conn.sendall(pack(29, 0, _b29role))
_b30role = build_30()
```

实测日志：

```
c002 -> cmd=818 seq=0 len=850 [42 触发 完整装备 真服原包]
c002 -> cmd=43  seq=39 len=345 [角色详情 真服原包]
c002 -> cmd=29  seq=0  len=38  [角色面板补推属性 Lv52]
c002 -> cmd=30  seq=0  len=96  [角色面板补推装备 11件]
```

面板随即恢复：战力 2987 / 气血 3626 / 攻击 376-416 / 防御 168，11 格全在。

### 7.4 注意：登录尾部那份 29/30 补推走不到
它挂在 `if ptr >= len(SEQ) and not quest_pushed:` 里，本次登录 `ptr` 没走到末尾
（客户端中途发 `42` 就走了另一条分支），所以只有 `42` 那条真正生效。
面板刷新靠 `42` 已足够；如果以后要修 HUD 顶栏，得把 29 补在 `17` 应答之后。

## 9. 网络：DNAT 命中计数 + 防误连兜底

（实测 `:80` 16 次、`:9000` 1 次）。filter 表新增 `KD_GUARD`：

```
-A KD_GUARD -d 124.223.56.189 -p tcp --dport 9000  -j REJECT --reject-with tcp-reset
-A KD_GUARD -d 124.223.56.189 -p tcp --dport 19000 -j REJECT --reject-with tcp-reset
```

不会撞到；只有 DNAT 丢了才会 RST —— 把「静默登进线上服」变成「明显连不上」。

## 11. 重启客户端后「武器在、饰品全空」，脱一次武器才出现（13:22 修复）

### 11.1 复现路径
重启客户端 → 登录 → 进游戏：饰品 4 格 + 鞋子是空的，武器能看见。
手动脱下武器（触发 `37`）后，`37` 回包里的 `30` 把饰品补了出来。

### 11.2 真因
「登录后补推 29/30」那段挂在

```python
if ptr >= len(SEQ) and not quest_pushed:
```

只有**回放序列全部跑完**才会执行。实测 13:09:46 那次登录，客户端发完 `1265`
就只发 `cmd=4` 心跳（既不发 `42`，也不再要新 seq），`ptr` 永远到不了末尾，
于是 29/30 一条都没补 —— 客户端只拿 `17` 画了武器（外观块里有），
首饰/鞋子没有数据源，就是空格。

### 11.3 修法
改挂在 `cmd == 1265`（客户端初始化最后一步）之后，一次性补 `29 + 30`：

```python
if not equip_pushed[0] and cur().has_char:
    _b29 = build_29(); conn.sendall(pack(29, 0, _b29))
    _b30 = build_30(); conn.sendall(pack(30, 0, _b30))
    equip_pushed[0] = True
```

`equip_pushed` 与 `login_pushed` 同生命周期（每条连接一个 `[False]`）。
`42` 分支补推完也置 `True`，避免重复。

## 12. 「绑定铜币-2202471 / 元宝-1749 / 绑定元宝-4050」是怎么回事

不是服务端扣钱，也不是存档丢钱。核对结果：

- `player_state_900000102.json` 里 `coin=101529`，`bind_yuanbao=0`，
  `tongqian=0`，`yuanbao=0`；服务端日志里历次 `28` 只有 101529/107529/110529/116529，
  **从来没有 230 万**。
- 2202471 + 101529 = 2304000：客户端本地缓存着旧会话的 2,304,000，
  收到真实 101,529 时按差额弹了负数飘字。

那 230 万来自**早期第 28 包只覆盖 u32 低 16 位**的 bug（`0x0023xxxx + 低16位`，
`build_28` 注释里记着「会出现 2305802 这种鬼数字」）。该 bug 早已修掉，
这次只是客户端缓存第一次和真实值对账。对账一次后缓存就等于真实值，不会再弹。

背包底栏实测也是 `0 / 0 / 0 / 101529`，与存档一致。
