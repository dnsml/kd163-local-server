## 客户端怎么连过来

客户端把服务器 IP 写死在 `server-list.xml`（`124.223.56.189`），三种接法：

1. **手机/模拟器 DNAT（最快，不改包）**
   ```bash
   su 0 iptables -t nat -A OUTPUT -d 124.223.56.189 -p tcp --dport 80 \
        -j DNAT --to-destination 129.204.52.72:80
   su 0 iptables -t nat -A OUTPUT -d 124.223.56.189 -p tcp --dport 9000 \
        -j DNAT --to-destination 129.204.52.72:9000
   ```
   缺点：设备重启后失效，每台设备都要设。

2. **改 APK 内置 `server-list.xml` 重打包**（推荐给玩家）
   把 `124.223.56.189` 全替换成 `129.204.52.72`，重签名。
   注意资源包 `mhsj_res.zip` 里也有同名文件，要一起改，否则客户端会把
   本地改过的覆盖回去。

3. **本地资源服当跳板**
   本机 80 端口的 `local_http.py` 已经会把资源里的 IP 替换成 `HOST_IP`：
   若把 `HOST_IP` 设成 `129.204.52.72`，客户端从本机 80 拉一次资源，
   `server-list.xml` 就变成新 IP。前提是本机 80 一直开着。

## 证书注意（实测更正）

客户端**把 PEM 整个内嵌在 `classes.dex` 里做 pinning**，握手后逐字节比对。
所以「只改 URL 不换证书」的做法行不通 —— 服务端换证书后，客户端握手成功
但一个字节都不发就断开（`handle_tls` 日志：`握手成功 … 收到字节 0`）。

正确做法（本次已落地）：**等长替换 DEX 内嵌证书**，生成 DER 长度必须与原来
完全一致的证书（`DER=808 / PEM=1151`），`work/gen_cert.py` 自动调整 serial
长度 + 一个固定 OID 扩展来凑足长度：

```bash
python work/gen_cert.py            # -> patch/newcert/exact_new.pem / pub.key
python work/dexpatch.py            # 内嵌 PEM 等长替换（delta=0）
python work/verify_dex.py work/apk_out/classes_new.dex
```

证书主体（与 APK 内嵌、服务端 `patch/exact.pem` 三处必须同一张）：

```text
subject=CN=129.204.52.72
X509v3 Subject Alternative Name: IP Address:129.204.52.72
DER=808  PEM=1151  （与原证书完全等长）
```

⚠️ 以后换 IP 要**同时**改三处：`classes.dex` 的 7 个 URL + 内嵌证书、`AndroidManifest.xml`
的 `client.apk` URL、服务端 `patch/exact.pem|key`。任一处漏了就是「连不上」或「握手后被断开」。

### ★ DEX 补丁必须等长（踩了两次）

第一版重建 `string_data` 区、把后续 section 整体平移（-7 字节），Android 直接拒加载：

```text
Failure to verify dex file ...: Offset(1605953) should be aligned by 4 for map.
Shorty vs. primitive type mismatch: 'I', 'Lcom/aiyou/views/UmengShareMenu$MenuAdapter;'
```

第二版加了 4 字节 padding，仍因偏移变化触发同一类校验错误。
最终方案：新字符串区**不超过原区时补零到原长度**（`delta=0`），所有 section 偏移不变：

```python
if len(block) <= old_span:
    block += b"\x00" * (old_span - len(block))
    delta = 0
```

改完补 header checksum（adler32）和 SHA-1，`work/verify_dex.py` 校验
magic / file_size / checksum / SHA1 / `map_off % 4` / section 递增 / MUTF-8 长度 / 各 off 越界，
全部 OK 才装。

### 为什么改包名不会把游戏改坏

先 dump 过 manifest 才动手，三条事实支撑：

1. **所有组件都是绝对类名**（`com.aiyou.mhsj.GameActivity` / `com.aiyou.mhsj.MainActivity` / `com.aiyou.mhsj.wxapi.WXEntryActivity`），
   没有 `.MainActivity` 这种相对名 → applicationId 变了，类路径不变，照样能解析。
2. **没有任何 provider / service / receiver**，所以不存在 `INSTALL_FAILED_CONFLICTING_PROVIDER` 的 authority 撞车。
3. **`classes.dex` 里点分包名出现 0 次**，只有 18 处类描述符 `com/kdxx/online/...`（两个充值 Activity + R 类），
   这些是真实类，本来就该保留旧命名空间。

所以本次只动 manifest 的两个字符串 + 图标，DEX 一个字都没碰。

### 两个必须注意的细节

- **字符串池要「整串相等」替换，不能子串替换**。`axmlpatch.py` 原来是 `s.replace(old, new)`，
  拿它改包名会把 `com.kdxx.online.recharge.RechargeActivity` 一起改成 `cn.kd163.online.recharge.*`
  → 这两个页面直接 ClassNotFound。`apk_coexist.py` 里改成 `repl.get(s, s)`。
- **池内条目数量不变**（只改内容、不增删），attribute 里的 string index 继续有效，不用重算。

### 数据隔离

DEX 里没有任何 `/sdcard`、`/storage/emulated` 硬编码，也没有共享 prefs 名，
所有状态都落在 `/data/data/<包名>/` → 两个包天然隔离，互不覆盖账号缓存。

## 本地版客户端重做（13:3x）——「撞回原版」的根因与修法

现场：


所以「服务端出示 `patch/exact.pem`（CN=129.204.52.72）」必然被客户端拒 → 握手后零字节断开。

修法不是改 IP（原版 IP 已经被 `work/net_fix.sh` DNAT 到本地），而是**换内嵌证书**：

1. `work/gen_cert_local.py` 生成**同构等长**新证书：CN/SAN=`124.223.56.189`、
   RSA2048、ext 同原版（BC critical CA:TRUE + SAN + SKI/AKI）、serial 20B，

2. `work/patch_dex_local.py` 用 `dexpatch.patch()` 把 DEX 里那 1150 字节 PEM 等长替换，
   `delta=0`（section 一个都不动），`verify_dex.py` 通过。
3. `work/repack_apk.py` 只换 `classes.dex`，`jarsigner` v1 签名 → `work/local/kd163_local_signed.apk`（118MB）。
4. 本地服改用本地证书起：`local_server3.py 9000 patch/local/exact.pem patch/local/exact.key`。
   自检：`ss.getpeercert(binary_form=True)` 的 sha256 与证书文件一致（`1096b29c…`）。

## 推送通道真正打通：DNS 层故障，不是全局限流（2026-11-27 22:0x）

上一节结论「关梯子就推不了」只对了一半。继续排查发现：

| 测试 | 结果 |
|---|---|
| `github.com` 域名 → 443 | ❌ TCP connect timeout（连不上，不是证书问题） |
| `140.82.112.4 / .113.4 / .114.4 : 443` | ✅ 全 OPEN |
| `20.205.243.166 / 20.27.177.113 : 443` | ✅ 全 OPEN |
| `curl --resolve github.com:443:140.82.113.4 …/info/refs?service=git-receive-pack` | ✅ **200** |
| 本机 7890 / 7891 / 1080 / 10809 / 2080 … 全端口探测 | ❌ 一个都没在监听（只剩 `FIN_WAIT_2`） |

结论：故障只在**域名这一跳**，TLS/鉴权/仓库权限全好，且**不需要梯子**。

做法：`work/gh_tunnel.py`（本机 CONNECT 代理，默认 `127.0.0.1:7899`）。
收到 `CONNECT github.com:443` 时按 IP 池依次尝试上游连接，其它域名交系统解析。
git 侧 TLS 的 SNI 仍是 `github.com`，证书校验照常通过。

```bash
bash work/gh_push.sh      # 起隧道 → push → ls-remote 校验 sha
```

实际结果：`91d2bd5..a5b94dd  master -> master`，**纯快进、没有强推**，
远端 `a5b94dd0d5eb37cdb7dc7938b18cd591c39daea7` 与本地完全一致。
第一次尝试出过一次 `OpenSSL SSL_read: unexpected eof`（隧道瞬时抖动），
重试一次即成功 —— 所以脚本保留了重试（`KD_PUSH_TRIES`，默认 3）。

两个坑记一下：

- 后台 `python work/gh_tunnel.py &` 直接被回收（和本地服 `nohup &` 同一现象），
  必须用后台任务跑；`gh_push.sh` 里改成脚本自己拉起子进程 + `trap EXIT` 收掉，自包含。
- `.git/refs/remotes/origin/` 里的文件会被这台机器的某个东西反复清掉：
  `git fetch` 明明打印 `[new branch] master -> origin/master`，`git show-ref` 却一条都没有，
  `git status` 一直 `[gone]`。补法是 fetch 后手工写 `printf '<sha>\n' > .git/refs/remotes/origin/master`。
  （不补也能 push，只是状态行难看，且 `gh_push.sh` 的「待推提交」列表会回落到最近 3 条。）

### 隧道本身的两个 bug（第一版 1/5 成功率）

- `_pipe()` 单向读到 EOF 时把**两个 socket 都** `shutdown(SHUT_RDWR)` ——
  上游发完 FIN，反方向可能还有数据在飞，一刀切就得到 `OpenSSL SSL_read: unexpected eof`。
  改成只 `dst.shutdown(SHUT_WR)`。
- 主线程 `t.join(timeout=30)` 之后无条件 `close()`：push 上传大包时客户端方向先结束，
  响应可能还要几十秒，超时就把连接关了。改成两个方向都 `join()` 等到自然结束。
- 拨号策略：单个 IP `connect` 超时 6s × 5 个 IP 会把超时预算全耗在死 IP 上
  （实测失败点在 TCP connect，`time_connect=0`，不是 TLS）。改成 2.2s/IP、
  总预算 14s、7 个边缘 IP 轮转重试。实测从 2/8 提到 **5/6**。

`gh_push.sh` 另加一步：推送成功后手工写 `refs/remotes/origin/<br>`，
因为这台机器上 git 自己写的远端跟踪引用会被清掉（`[gone]`）。
