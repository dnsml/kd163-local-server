# 抓包日志说明（怎么看 `logs/relay.log`）

> 这份文件是**别人在运营的那台服务器**（下文统称「线上服」）的完整对话记录，
> 也是本地服所有协议细节的来源。任何人接手这个项目，先读这一份就够。

## 1. 文件在哪、多大

| 文件 | 大小 | 说明 |
|---|---|---|
| `logs/relay.log` | 约 2.2 MB（十几万行） | 主记录。全部已入库，克隆下来就能看 |
| `logs/relay.log.bak_1233` | 约 2.0 MB | 冗余副本（是 relay.log 的前缀片段），**不入库** |
| `logs/relay_raw.bin` | 二进制 | 原始字节流，一般不用 |

`relay.log.bak_1233` 不用管：它的内容能在 `relay.log` 里逐字节找到，
只是早期怕写坏日志留的一份备份。判断命令：

```bash
python -c "m=open('logs/relay.log','rb').read();print(open('logs/relay.log.bak_1233','rb').read() in m)"
```

## 2. 行格式

```
[2026-11-24 23:52:30] C->S cmd=819    seq=4477  len=4 hex=cd28420b
[2026-11-24 23:52:30] S->C cmd=1      seq=4477  len=29 hex=04bb...
```

* `C->S` 客户端发、`S->C` 服务端回（`S->C seq=0` 的是**服务端主动推送**）
* `len` = 帧总长（含 6 字节头），`hex` 是载荷
* ⚠️ **`hex` 最多 160 个字符（80 字节）**，长包在日志里是截断的。
  需要完整包时看 `logs/relay_raw.bin`。

## 3. 帧结构（明文，9000 端口）

```
[u16BE len][u16BE cmd][u32BE seq][payload]
len = 6 + len(payload)
```

* 第一条 TLS 握手（首字节 `0x16`）走 `/auth`，游戏协议本身是明文。
* 短串编码：`0xA0 | len` + 内容。
* 整数编码（varint 风格）：
  * `< 0x80` → 单字节
  * `0x80..0xFF` → `cc` + 1 字节
  * `0x100..0xFFFF` → `cd` + 2 字节
  * 更大 → `ce` + 4 字节
  * 例：`cd 28 42` = `0x2842` = 10306；`ce 00 20 59 a5` = 2120101

## 5. 自己再抓一份

```bash
# 方式 A：透传转记录（客户端连 本机19000 → 线上服:9000）
python relay.py

# 方式 B：本机代理（把 124.223.56.189 指到本机，80 与 9000 一起记录）
python capture_proxy.py
```

抓完直接追加到 `logs/relay.log`，格式不变，本项目所有解析脚本都认这个格式
（日期前缀可选，旧日志 `[HH:MM:SS]` 仍然能读）。

## 6. 读日志的三条纪律

1. **先对齐 seq 再下结论**：`S->C` 的 `seq` 等于请求的 `seq` 才是应答，`seq=0` 是推送。
2. **`len` 和 `hex` 长度要能对上**：对不上就是被截断了，别拿去当"完整包"用。
3. **同一操作抓三次**再定结构，单个样本容易把「某次特殊状态」当成普遍规律。
