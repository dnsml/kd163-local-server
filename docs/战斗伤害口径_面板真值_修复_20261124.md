# 战斗「莫名其妙胜利」修复 —— 伤害口径改成面板真值

2026-11-24 17:5x ｜ 用户反馈：「和装备没关系是计算有问题感觉 会莫名其妙胜利」

## 现象

- 打任何小怪都是 **需 1 回合**，进场点一下就「战斗胜利」。
- 脱掉武器也一样赢，用户判断「和装备没关系」。
- 服务端日志实证（修复前）：

```
[16:45:52] 开战 作乱小妖(lv13) 输出438/回合 需1回合
[16:47:42] 开战 疑心魔(lv23)   输出832/回合 需1回合
[17:16:35] 开战 心魔(lv5)      输出1218/回合 需1回合
[17:39:01] 开战 摄心魔王(lv23) 输出1342/回合 需2回合
```

## 根因

`battle.BattleSession` 一直只用 **Levelup.xml 裸属性**（不含装备/强化/妖灵），
为了让低等级号打得动，又乘了一个假的等级系数：

```python
base_deal = atk_avg * (1.0 + 0.14 * lv) * crit_mult
```

- Lv38 逍遥：Levelup 裸攻 174~180 → atk_avg 177，×（1+0.14×38=6.32）× crit 1.2 ≈ **1342**
- 而怪的血量是按「玩家真实攻击」配的：摄心魔王 1500 血，两下就没了。

也就是说：**等级系数把伤害吹了 6 倍，装备的加减反而被淹没**，
所以「脱武器也一样赢」。

## 修法

`BattleSession.__init__` 新增 `attrs` 参数，由服务端把 **29 面板同一口径**
的属性传进来（`panel_attr()`，含装备/强化/大师/套装/妖灵）：

```python
at = attrs or {}
hp_base = at.get("hp_max") or st["hp_max"]
atk_min = at.get("attack_min") or st["atk_min"]
...
_gain = 1.0 if self.panel_based else (1.0 + DMG_LEVEL_GAIN * self.lv)
self.base_deal = max(1.0, atk_avg * _gain * self.crit_mult)
```

- 有面板（正常游戏内）→ **不再乘等级系数**，伤害 = 面板攻击均值 × 暴击系数。
- 无面板（离线单测/探针）→ 退回旧公式，行为不变。

`local_server3.py` 的 145 分支：

```python
_ba = {k: panel_attr(k) for k in ("hp_max","mp_max","attack_min",
                                  "attack_max","defense","crit")}
battle_sess = battle.BattleSession(mob_id, BT, cur().cls, cur().level,
                                  pet=..., name=cur().name, attrs=_ba)
```

## 修复后

| 场景 | 输出/回合 | 回合数 |
|---|---|---|
| Lv38 满装备打摄心魔王(1500血) | 326 | **5** |
| Lv38 脱掉槽1（12108） | 237 | **7** |
| Lv1 未转职打仙界守卫(80血) | 11 | 8（可扛 10 回合，仍可胜） |

实测（探针 `work/probe_journey_defense.py`，怪 2090101 日曜使者 1939 血）：

```
151 玩家血2019 输出371/回合 承伤14/回合 需6回合 可扛145回合 -> 可胜
146 防御 x6 -> 148 依次 50B(回合1~5) / 32B(第6回合结束)
```

装备现在真的影响输出（326 → 237，差 27%），战斗也回到 5~7 回合。

## 仍存在的一个「观感差」（待定，未改）

客户端每回合只给自己的怪血条扣 **8~16 点**（logcat：`set object(131302) hp damage = 16,
m_hp = 434`），这个数值是客户端本地按模板号算的，服务端改不了。
于是 450 血的怪打完 2 回合时，血条还剩 96%，却已经弹出「战斗胜利」——
这也是「莫名其妙胜利」的另一半观感。

要让血条自然走空，只能把 **151 里的怪血改成 `16 × 回合数`**（如 450 血 2 回合 → 发 32）。
以前发折算值（心魔 32）崩过客户端，但那次的真凶是 `enc_val` 整数分档，
现在编码已修，理论上安全 —— 需要一次实机验证再决定是否切换。
