## 10. 2026-11-22 22:40 补丁：世界BOSS「战斗里没有敌人 / 出不去」

### 10.1 根因：151 的血量是变长编码，不能硬塞一个字节

`151` 开战包里怪物的 当前血 / 最大血 用的是和 113 对象 ID 同一套变长整数：

```
< 0xCD      -> 1 字节
< 0x10000   -> 0xCD + u16BE
其它        -> 0xCE + u32BE
```

旧 `build_open()` 写的是 `b[28]=b[29]=min(255,hp)`：

- 仙界守卫 hp=80 -> `0x50`，合法，所以小怪战斗一直正常；
- 九尾狐 hp=11228、穷奇 hp=176308 -> 都被截成 `0xFF`，而 `0xFF` 在这套编码里

  是**非法前导字节**，客户端解析怪物列表时直接丢掉这只怪。

logcat 实证（22:25:31，穷奇）：

```
ObjectBattleView for monster created, id = 51065
ObjectBattleView destroyed, id = 51065        <- 建完立刻销毁
target(7) not exist !!!!                      <- 之后每回合都在找不存在的 7 号
actor = 7, data = 11110101, target = 1, action = 1
```

所以画面就是「只有自己、没有敌人」。**场景本身不空**（22:32 截图：神剑冢里

白虎 Lv.50 / 邪剑仙 Lv.55 / 穷奇 Lv.55 都在，头顶有攻击图标）。

### 10.2 修法

`battle.enc_val()` 实现上面的变长编码，`build_open()` 改成

```
OPEN_TMPL[:24] + 怪ID(4B) + enc_val(hp) + enc_val(hp) + OPEN_TMPL[30:]
```

- 小怪（hp<0xCD）包长仍是 35B，和真服样本 `010c06...50500000020107` **逐字节一致**；
- 世界BOSS 包长变 39B（`cd0393`），客户端能正常解析。

### 10.3 副产物：一场仗最多 15 回合的血量

真血量的世界BOSS（穷奇 176308）按 lv10 玩家 66 点伤害要 2600+ 回合，只能等

`BattleSession._effective_hp()`：**本场血量 = min(配置血量, 单回合伤害 × 15)**。

### 11.3 「打输」这条路不通（实测结论）

## 12. 2026-11-22 23:35 战斗机制重写（取消「永远胜利」）

### 12.1 之前为什么是「永远胜利」

上一版为了让怪「能死」，把怪血量裁成 `min(配置血量, 我方伤害 × 可打回合)`，

而且玩家永远不会被打死 —— 本质是作弊，所以每场都赢。

### 12.2 客户端的硬约束（决定机制只能这么做）

| 事实               | 证据                                                          |
| ---------------- | ----------------------------------------------------------- |
| 客户端每回合对怪固定 16 伤害 | logcat `set object(900001) hp damage = 16`（世界BOSS 也是 16）    |
| 客户端每回合固定掉 13 血   | logcat `set object(12) hp damage = 13`，m_hp 343→330→317→304 |
| 血条只显示百分比         | 战斗截图 65% / 95%，从无绝对数值                                       |
| 血条初始值取 151 里的血量  | 把 151 玩家血填 104，客户端就从 104 开始按 13 掉                           |

**抓手**：客户端血条 = `151 血量 ÷ 每回合固定伤害`。

只要把 151 的血量填成「回合数 × 16 / 回合数 × 13」，

血条就会在服务端判定的那一回合刚好归零，玩家看不到任何数值差异。

### 12.3 新机制（battle.py v2）

```
玩家：Levelup.xml   class+level -> hp_max / atk_min,max / defense / crit
怪物：Monster.xml   hp_max / level / monster_type
怪物攻击：没有字段，按等级拟合 mob_atk = 4 + 1.2*lv
等级压制：gap = clamp(1 + 0.035*(mob_lv - lv), 0.55, 1.8)
输出：pdmg = atk_avg * (1 + 0.14*lv) * (1 + min(0.3, crit/400))
承伤：mdmg = mob_atk * gap * (1 - 减伤)
kill = ceil(怪血 / pdmg)    die = ceil(玩家血 / mdmg)
kill <= die 才能赢，否则被怪打死；40 回合还没完 = 力竭判负
```

两本账都记「回合数」（`atk_rounds` / `hit_rounds`），血量只是显示折算：

`151 怪血 = 16 × kill`，`151 玩家血 = 13 × die`（`CLIENT_PDMG` / `CLIENT_MDMG`）。

## 14. 真服背包与物品使用协议（23:5x 定案，取代之前的猜测）

### 14.1 指令表

| 指令    | 方向   | 载荷                | 含义                           |
| ----- | ---- | ----------------- | ---------------------------- |
| `181` | C->S | 空包                | 打开／刷新背包                      |
| `181` | S->C | `[0x40][n]` + n 条 | 背包**全量**                     |
| `178` | S->C | `[0x40][n]` + n 条 | 背包**全量推送**（结构同 181，物品变动后主动推） |
| `182` | C->S | `[格子 1B][数量 1B]`  | **使用／穿戴／打开** 该格物品            |
| `182` | S->C | 空包                | 只有 ACK，所有状态走别的推送             |

`182` 的数量字节写 **0 = 全部使用**（实证：`00 00` 把 9 张铜钱卡一次用光、

`0a 00` 把剩 4 本见闻录用光）。

### 14.2 条目格式（7 字节，字段都是变长整数）

```
[pos 1B][item_id 变长][enh 1B][bind 1B][num 1B]
```

- `pos`：格子下标，0 起，**绝对槽位**。用掉一格后其它格不前移（实测 15:38:17 只剩 `00 02 03`，01 就是空的）；新物品填进最小空格。
- `enh`：装备强化/附加等级，非装备恒 0（天枢剑[二阶] = 8）。
- `bind`：实测恒 1，疑似绑定标志。
- `num`：堆叠数量，客户端按这个显示 `xN`；掉到 0 时该格子**从增量包里消失**（= 删除）。

样本（15:39:41 推送，9 件，65B）：

```
40 09 | 00 cd2be3 08 01 01 | 01 cd5118 00 01 01 | 02 cd5209 00 01 01 | ...
 类型 9件  格0 天枢剑 +8     格1 45倍返利    格2 5级新丁礼包
```

**178 不是增量包**：它和 181 的包体一模一样，都是全量快照，客户端整包替换列表。

用光一格后该格直接不在包里 —— 删除靠「缺席」表达，别写成 upsert 增量。

（这条差点写错：一开始按 7 字节/条 反推出「只推变化格」，是 15:38:22 那个只剩 `02 03`

的 16B 包把它纠正过来的。）

### 14.6 顺带把「整理闪退」的根因定死了

客户端点「整理」发的是 **`181` 空包**（不是 `182`）。我们本地服当时 `cmd==181`

本地排序函数拿不到列表就 abort。

现在有了正确的包体，本地服只要改两行：

```python
if cmd == 181:
    return 181, bag_proto.build_181(BAG), []   # 16 格全量，pos 从 0 开始
if cmd == 182:
    pos, num = bag_proto.parse_182(payload)    # 使用物品
```

## 16. 线上服充值时实测：元宝 +880 是服务端主动推的，客户端没发任何包

用户点「商城 → 立即充值」，元宝从 869 变成 1749（+880）。抓包结果有点反直觉：

**整条充值链路在游戏协议里是空的。**

### 16.1 那 3 分钟的完整原始记录

```
[00:04:22] C->S cmd=4   seq=260  心跳
[00:04:32] C->S cmd=4   seq=261  心跳

[00:04:44] S->C cmd=28  seq=0    len=73   ← 元宝在这里变了
[00:04:44] S->C cmd=30  seq=0    len=86
```

`00:03:00 ~ 00:05:20` 之间，`C->S` 里**除心跳外一条都没有**。没有充值请求、

### 16.2 数值精确对上

```
                                ^^^^^^ 不变   ^^^^^^ 869 -> 1749
```

`cd0365` = 869 → `cd06d5` = 1749，**+880**，和界面上看到的数字完全一致。

### 16.3 28 包里的货币字段（修正第 15 节的误判）

| 字段                  | 本次值          | 含义       | 证据                      |
| ------------------- | ------------ | -------- | ----------------------- |
| `cd0365` → `cd06d5` | 869 → 1749   | **元宝**   | 充值 +880                 |
| `cd0fbe` → `cd0fd2` | 4030 → 4050  | **绑定元宝** | 用 `20432 10绑定元宝` x2，+20 |
| `cd0960` → `cd3070` | 2400 → 12400 | 绑定铜币     | 15:38 用绑定铜钱卡 +10000     |
| `ce002328`          | 9000         | 待定（多次不变） | —                       |
| `cd03fc`            | 1020         | 待定       | —                       |
| `cd2166`            | 8550         | 待定       | —                       |

之前第 15 节把 `cd0fbe` 当成元宝，是因为那次的 `20432` 名字里带"元宝"。

充值这一刀把它切开了：**元宝走 `cd0365`，绑定元宝走 `cd0fbe`，两者独立。**

### 16.4 这意味着什么

- 客户端侧的"商城/立即充值"只是**打开界面**（大概率是跳外部支付页或纯本地 UI），

  游戏 TCP 上不产生任何请求。
- 加元宝的动作发生在服务端：要么是支付回调，要么是后台/GM 直接改。

  表现出来就是「客户端什么都没发，元宝自己到了」。

  `113`（`6601 ce000dbba2 2a 010000`，`900002` 疑似充值活动 id）只是到账/活动通知，

  它出现两次（23:59:28 和 00:04:39），不携带金额。

> **⚠ 第 16 节的结论已被第 17 节推翻。** 那 880 不是"充值"，是「充值福利」页
>
> 每天免费领的 88 元额度（×10 = 880 元宝）；请求走的是 HTTP 80 的 `/api/recharge/*`，
>
> 不在游戏 TCP 上，所以当时在 9000 端口一条都看不到。

## 17. 「充值福利」每日 880 元宝：不是充值，是 HTTP 接口每天白领（00:09 抓包定案）

第 16 节说"充值链路在游戏协议里是空的、没包可抓"——**只对了一半**。

用户在充值福利页点的是「每日免费领取」，走的是 **HTTP 80 的 JSON 接口**，

压根不经过 9000 端口的游戏 TCP。所以 9000 上当然干净。

界面原话：「每日免费领取 88 元充值额度（880 元宝），每天北京时间 00:00 重置」

### 17.1 抓到的真实请求（tcpdump，明文）

在模拟器上 `tcpdump -i wlan0 -A 'tcp port 80'`，点一次「刷新」立刻出包：

```http

Accept: application/json

{"uid":"1784366","token":"W11nwqduOoif6bvgnIYWyQOrmyRnqXDi02yrkq7C-ZM"}
```

响应（200，324 字节）：

```json
{"ok":true,

 "daily_amount":88,        // 每日额度（元）
 "daily_amount_yuan":88,
 "daily_claimed":true,     // 今天领过了
 "day":"2026-11-23",
 "gold_per_yuan":10,       // 1 元 = 10 元宝  → 88 元 = 880 元宝
```

### 17.2 接口表

| 方法   | 路径                     | 载荷                | 说明                        |
| ---- | ---------------------- | ----------------- | ------------------------- |
| POST | `/api/recharge/status` | `{"uid","token"}` | 查状态，含今日是否已领               |
| POST | `/api/recharge/daily`  | `{"uid","token"}` | **领取**（401 而非 404，端点确实存在） |

实测鉴权：

```

→ 401 {"ok":false,"error":"身份认证失败，请重新登录"}

POST /api/recharge/daily   {"uid":"1","token":"x"}
→ 401（同上，说明路径对）
```

**没有任何签名、时间戳、nonce**，只认 `uid` + `token`。token 校验在服务端。

### 17.3 数字完全自洽（证明昨天也领过）

```
11-22 领 880 元宝 → 花掉一些，剩 869
11-23 00:04 领 880 → 869 + 880 = 1749   ← 28 包里 cd0365→cd06d5 实测
total_gold 1760 = 880 × 2               ← 累计发放
total_yuan 176  = 88 × 2                ← 累计额度
```

`total_gold 1760` 比当前 `gold 1749` 多 11，正好是这期间花掉的元宝。

三条线交叉验证，说明「每日 88 元 / 880 元宝」是**每天都能领**，不是一次性活动。

### 17.4 完整链路（两段，分别在两个端口）

```
[客户端] --HTTP 80 POST /api/recharge/daily--> [nginx:124.223.56.189]
                                                        |
                                                  写库：元宝 +880、累计额度 +88
                                                        |
[客户端] <--TCP 9000 S->C 29 / 28 / 30--------- [游戏服]
                       ↑ 5 秒后推，28 里 cd0365 变 1749
```

00:04:39 点领取 → 00:04:44 游戏服推 `29`+`28`+`30`，元宝 869→1749。

**HTTP 那半段在 9000 端口永远看不到，这就是第 16 节误判的原因。**

（顺带排除：`113` 不是到账通知，它每隔几分钟就来一条

`6601 ce000dbba2 2a 010000` / `6601 ce000dbba1 15 0000`，是周期性状态位，与充值无关。）

### 17.5 token 从哪来：登录包 cmd=17 明文带上

客户端**主动提交**，不是服务端下发。登录时第一条业务包：

```
[23:34:33] C->S cmd=17 seq=2 len=58
01 cc9702 a7 "1784366" da 00 2b "W11nwqduOoif6bvgnIYWyQOrmyRnqXDi02yrkq7C-ZM"
          └─┬──┘ └──┬───┘ └──┬──┘ └───────────── 43 字节 ─────────────┘
           tag    长度 7    u16 长度 43    token
```

- `a7` = `0xA0 | 7`，短字符串编码（长度在低 4 位）；`a6` 同理（S->C 里 `a6 e8908c e696b0` = "萌新"）
- token 43 字符 base64url = **32 字节随机**，形如会话票据
- 客户端存在 native 层，`shared_prefs` 里只有 `username=1784366` 和 `device_id`

**这意味着复刻本地服时，登录应答里必须原样吐出同一个 token**，否则网页/活动面板调

`/api/recharge/*` 会 401。本地服现在已经能解析 cmd=17，把 token 存下来再回传即可。

### 17.6 客户端结构

```
com.kdxx.online.recharge.RechargeActivity        ← 充值福利面板（原生 Activity，不是 WebView）
com.kdxx.online.recharge.GardenLogActivity       ← 另一个页面（/api/garden/logs）
```

dex 里硬编码：

```
http://124.223.56.189          +  "/api/recharge/"  +  "status" / "daily"
```

`patch_apk.py` 换 host 时这 7 处会一起改，所以**自建服只要在 80 端口实现这两个 POST 就能用**。

### 17.7 能不能重复领

- `daily_claimed` / `day` 都在**服务端**，客户端改不了界面上的按钮也刷不出第二次
- 重置按 `+08:00` 的 00:00，`next_reset_at` 明确返回，不依赖客户端时钟

  （另有 `clock_rollback` 字段，说明服务端会检测改时间）
- 唯一可能的口子是服务端是否信任客户端传的 `day`——但本接口 body 只有 uid/token，

  **没有 day 参数**，所以这条路也堵死

结论：**没法刷，只能每天老老实实领一次。**

### 17.8 一键领取（自用）

```bash
curl -s -X POST http://124.223.56.189/api/recharge/daily \
  -H 'Content-Type: application/json' \
  -d '{"uid":"1784366","token":"<登录包里的 43 位 token>"}'
```

token 每次登录可能变，稳妥做法是从 `relay.log` 的 `cmd=17` 里实时取。

## 19. cmd=28 字段表定案 + 货币读写工具 grant.py（00:20 全量回归）

用户报「元宝 1749 / 绑定元宝 4050 / 铜钱 0」。三个数拿去和 96 个 `28` 包对账，

**全部精确命中**，顺带把一个藏了很久的解析错误挖出来了。

### 19.1 先纠错：`0xCC` 是 1 字节载荷，不是 2 字节

之前把 `0xCC` 和 `0xCD` 都当成 u16 前缀（都吃 3 字节），于是 `cc d2` 被读成

`cc d2 cd` 一个值，后面的字段整体偏移。凑巧的是偏移在 `idx13` 附近自己又对齐了，

所以货币下标没崩，但字段数和下标全错了一位。

正确规则：

| 前缀          | 载荷            | 例子                         |
| ----------- | ------------- | -------------------------- |
| `< 0xCC`    | 无（本身就是值）      | `0a` = 10                  |
| `0xCC`      | **1 字节**      | `cc d2` = 210              |
| `0xCD`      | 2 字节          | `cd 0f d2` = 4050          |
| `0xCE`      | 4 字节          | `ce 00 23 28 00` = 9000    |
| `0xA0-0xCB` | 短字符串，长度在低 4 位 | `a7 "1784366"` / `a6 "萌新"` |

改对之后，**96 个 `28` 包全部逐字节往返一致**（解析 → 重编码 → 原文完全相同，

`grant.py` 里有自检）。这才叫解析对了；之前 55/96 只是"看起来能读"。

### 19.4 「铜钱 0」不是读错，是你真的从来没有过

`铜钱`（idx20）在 **96 个包里一次都没有非 0**（脚本判定 `any(v[20]!=0)=False`）。

也就是说这个角色从上线到现在，**所有进账都进了绑定铜钱**（230 万），

玩法（不是"绑定铜钱"）做一次，`grant.py` 会立刻显示 idx20 从 0 变正数。

### 19.6 坑

- **下标是"第几个值"，不是字节偏移**。uid 长度、角色名字节数一变，偏移全变；

  必须先 tokenize 再按下标改，最后整包重编码（`grant.py` 就是这么做的）。
- 改值时如果新值跨了编码档（比如 200 → 100000，`cc c8` 变 `ce 000186a0`），

  包长会变，**`len` 头要跟着重算**，`grant.py` 自动算。
- 别直接改 `bind`/`enh` 那些字节，`idx` 是唯一稳定坐标。
- 推 `28` 时客户端只在"当前界面"刷新数值；背包界面开着的话还要配一条 `29`（35B）

  才会立刻变，否则要等下一次属性推送。

**失败（15:32:55）**

```
C->S cmd=371 len=5   cd 4f 61 07 01
S->C cmd=1   len=20  "对应货币不足"
```

`cd4f61` = 20321 = **1级宝石盒**（desc：`打开可随机获得一级宝石一个,商城获得`）。

紧接着客户端发 `cmd=500` 空包，服回 `500` + `00`（大概率是关闭购买弹窗/刷新列表）。

**成功（15:51:25）**

```
C->S cmd=371 len=5   cd 50 ff 01 01
S->C cmd=371 len=1   01                 ← 成功标志
S->C cmd=29  len=35
S->C cmd=28  len=73                     ← 元宝 870 → 869
S->C cmd=30  len=82
S->C cmd=178 len=114                    ← 背包重推
```

`cd50ff` = 20735 = **百年妖丹**，Item.xml 原文：

「…元宝商城特价为每个 1 元宝…」

**元宝正好 -1**，和描述里的价格完全吻合。

### 20.2 载荷格式：`[商品ID 变长][货币类型 1B][数量 1B]`

关键在于两个字节的顺序，靠 20321 那次才分清：

| 样本          | ID    | 第 2 字节 | 第 3 字节 | 结果                |
| ----------- | ----- | ------ | ------ | ----------------- |
| 20321 1级宝石盒 | 20321 | `07`   | `01`   | **货币不足**（元宝有 870） |
| 20735 百年妖丹  | 20735 | `01`   | `01`   | 成功，扣 1 元宝         |

如果第 2 字节是数量、第 3 字节是货币，那 20321 就是"买 7 个、花 1 元宝"，

在元宝 870 的情况下**不该失败**。所以只能是：

**第 2 字节 = 货币类型，第 3 字节 = 数量**。

- `01` = **元宝**（20735 扣的就是元宝，实测 870→869）
- `07` = **铜钱**（20321 走铜钱，而这个角色铜钱恒为 0 → 必然"不足"，见第 19.4 节）

这条和第 19 节完美咬合：不是随机失败，是它要的货币你正好一颗都没有。

### 20.3 应答规则

| 情况       | 服务端回什么                                            |
| -------- | ------------------------------------------------- |
| 成功       | `371` + `01`，然后 `29` → `28`（扣钱）→ `30` → `178`（入包） |
| 失败（货币不足） | **只回 `cmd=1` 文本，不回 371**                          |

失败时不回 371 这点很重要：如果服务端回了 `371 01` 却又没给东西，

客户端会认为买成功了、界面扣了钱，但背包里没有，表现就是"买了但没到账"。

### 20.4 本地服为什么"买不了东西"

`local_server3.py` 里其实已经写了 371 分支，但有三个问题：

```python
if cmd == 371:
    # payload = [3B 商品ID BE][u8 数量][u8 货币类型]   ← 顺序反了
    return 371, b"\x01", [29, 28, 30, 178]
```

1. **两个字节的顺序写反了**（写的 `[数量][货币]`，实际是 `[货币][数量]`）。

   因为两次样本都是 `xx 01 01`，反了也看不出来，一旦遇到 `20321 07 01`

   （买铜钱商品）就会把 07 当数量。
2. **从不扣钱**：直接把 `29/28/30/178` 原样重放，元宝数字不变。
3. **从不给东西**：`178` 是回放样本，里面没有刚买的商品，客户端刷新后背包没变化。

三条叠加，玩家看到的就是"点了购买，没反应/没到账"。

正确做法（伪代码）：

```python
if cmd == 371:
    gid, cur, cnt = shop_proto.parse_371(payload)   # [id][货币][数量]
    price = shop_proto.price(gid, cur)              # 单价 × cnt
    if balance(cur) < price:
        return 1, text("对应货币不足"), []          # 只回文本，不回 371
    balance[cur] -= price
    bag_add(gid, cnt)
    return 371, b"\x01", [29, 28, 30, 178]
```

`29` 必须在 `28` 前面（96 个包无一例外，见第 19 节），否则客户端不认这次属性刷新。

### 20.5 还没定

- **货币类型的完整枚举**：已确认 `01`=元宝、`07`=铜钱，其余（绑定元宝 / 绑定铜钱）

  没有样本。买一次绑元商品就能补上。
- **单价从哪来**：客户端不发价格，服务端自己查表。商品价格不在 `Item.xml` 里

  （那里只有描述文字），应该在 `Shop.xml` / `Mall.xml` 之类的配置里，需要再翻。
- **数量上限 / 限购**：没有样本。

## 21. 「自己的服进不去」排查：DNAT/adb reverse 丢了，不是服务端坏了（00:35 定位并恢复）

现象：点开 `com.kdxx.local1`，卡在启动页弹「检测资源版本信息失败」，点确认重试没用；

### 21.1 排查过程（四步排掉三个假嫌疑）

1. **服务端没崩**：9000 端口仍在 LISTENING（pid 10796），但 `logs/server.log` 停在 23:35，

   之后再没有任何连接 —— 说明客户端压根没连过来，不是服务端挂。
2. **不是坏包导致闪退**：闪退发生在登录之前（服务端零日志），且每次启动必崩，

   与本服下发内容无关。
3. **磁盘正常**：`df` 显示 23G 可用，日志里那句 `No space left on device` 是 cgroup

   线程数限制，不是真的没空间。
4. **资源清单确实拿不到**：客户端日志

   `KDXXOnlineHttp: http://124.223.56.189/assets.txt`，随后弹「检测资源版本信息失败」。

### 21.2 真正原因：两条基础设施同时丢了

这套共存方案的路由**不是靠改包，也不是靠 hosts**（客户端用的是 IP 字面量，

hosts 对 IP 不生效 —— 这点我一开始判断错了），而是：

```

iptables -t nat OUTPUT -m owner --uid-owner 10060 -p tcp --dport 9000 -j DNAT --to-destination 127.0.0.1:9000
                         ↑ 配合 adb reverse tcp:8080->host:80 / tcp:9000->host:9000
```

检查时发现：

- `adb reverse --list` **是空的**（三条隧道全丢）
- `iptables -t nat -L OUTPUT` 里 **没有 10060 的两条 DNAT**

于是：客户端按原样连 `124.223.56.189` → 走真服 → 真服的 `assets_md5=5efc42ed…`

和包内 `mhsj_res.md5=8c6ee66e…` 不一致 → 要求热更 → 热更走不到 → 弹窗失败 →

点确认重试还是失败 → 某些情况下渲染线程空指针闪退。

### 21.3 为什么之前能用、现在不行

- `work/probe_switch.sh` 里设备号**写死为 `127.0.0.1:5555`**，而实际设备是 `emulator-5554`，

  模拟器重启后脚本直接失灵 —— 规则没加上，但没人发现，因为界面上只显示"进不去"。
- `adb reverse` 会在 adb 重连 / 模拟器重启后全部失效，是易失状态。

```python
return 371, b"\x01", [29, 28, 30, 178]
```

只回了「成功」字节 `01`——客户端拿到 `01` 就播成功动效，

### 23.3 协议（真服 21:29 / 00:49 实证）


## 25. 【重要坑】把 idx12 写成 0 会让客户端「进战斗闪退」

### 25.1 现象

玩家：「为什么战斗进去闪退」。服务端日志：

```
[01:02:05] c003 -> cmd=145 ACK + 151 [... 玩家血48 ...]
```

客户端 logcat：

### 26.1 架构

```
浏览器  ──HTTP──>  admin_server.py (127.0.0.1:8899, 只跑标准库)
                        │  写 logs/gm.cmd
                        ▼
              local_server3.py 的 gm_watch 线程（每秒扫一次）
                        │  执行 → save_state() → 推 29/28/30/178 给在线连接
                        ▼
                  客户端当场刷新（不用重登）
```

走文件而不是 socket：不用给游戏服再开管理端口、不用重启，  
后台随时能改数值，而且断线也不影响。

### 26.2 功能

- 角色数值卡：元宝 / 绑定元宝 / 铜钱 / 绑定铜钱 / 阅历，带 `+1万/+10万/归零`
- 等级经验卡：`等级 +1`、`经验 +1万`、`等级清零`（危险操作，二次确认）
- 背包格子：显示 `格号 / #id / 名称 / 数量`，可单格删除
- 发放道具：中文名搜索（3504 个道具）→ 选数量 → 发放
- GM 指令台 + 快捷按钮（+10万元宝 / 清空背包…）
- 服务端日志实时尾巴（2.5s 刷新，输入框聚焦时暂停）

### 26.3 GM 指令

```
元宝 +100000        绑定元宝 =9999     铜钱 +1000000
阅历 +10000         等级 +1            经验 =2827
物品 20432 10       删除 3             清包
```

### 26.4 启动

```bash
python local_server3.py 9000 patch/exact.pem patch/exact.key   # 游戏服
python admin_server.py 8899                                    # 后台
# 浏览器 http://127.0.0.1:8899
```

### 26.5 注意

- 后台绑 `127.0.0.1`，不对外网开放。
- `等级` 能改，但**改成 1 会让战斗数值极低**（玩家血 48），  
  改完记得改回去；`等级清零` 按钮已加 `confirm()`。
- 数值以 `player_state.json` 为准（游戏服每次改动都落盘），  
  `status.json` 只用来拿在线人数。

## 28. 为什么「买的皮肤/时装」用不了（含一次误吞道具的教训）

### 28.1 真服穿戴协议（23:59:50 实证）

```
C->S 182  0f 01                      点「使用」时装/装备
S->C 182  len=0                      空 ACK
S->C 29 -> 28 -> 30                  刷属性/职业
S->C 1922 len=48                     装备/时装栏 全量
S->C 1931 len=35                     装备栏（含对象 ID）
```

## 30. 真服实测对照：翅膀「面板有、地图无」是原生行为

### 30.1 怎么验证的

用 relay（纯 TCP 透传，不解密）把 `com.kdxx.online` 的 9000 流量按 UID 导到本机 19000，  
只影响那一个包，本地服的共存规则不动：

```bash
adb reverse tcp:19000 tcp:19000
iptables -t nat -A OUTPUT -m owner --uid-owner 10058 -p tcp --dport 9000 \
        -j DNAT --to-destination 127.0.0.1:19000
```

登录真服（account=1784366，角色「萌新」10 级，战力 1020）。

### 30.2 实测结果

| 观察点                | 真服                | 本地服         |
| ------------------ | ----------------- | ----------- |
| 角色面板预览             | **有白色羽翼**         | 有（1922 生效）  |
| 地图场景               | **没有**            | 没有          |
| 别的玩家               | 紫色/蓝色翅膀正常显示       | —           |
| 点衣柜翅膀格子 → `116 03` | 回 **「本服尚未恢复此功能」** | 同样回这句（回放一致） |

结论：**这不是我们少了哪个包，是这个客户端版本对「自己」就不画地图翅膀。**  
翅膀面板（`116 03`）在真服也是关的，所以「展示/收起」那条命令真服也抓不到。

### 30.3 附带收获

- `837` = 请求衣柜（时装列表），真服回 `838`：  
  `09` + 9 条 `[ce 00015fa4 00 ff]`（对象 ID + 状态 + 有效期）→ 65 字节
- `1922/1931/1932` 的字节我们和真服**完全一致**，角色面板能正常显示，说明穿戴数据没问题
- 地图上别人的翅膀来自 `cmd=47`（周围玩家列表，条目里带外观），**不是** 1922
- 翅膀系统开启等级 40（形象卡描述原文：`在 40 级翅膀系统开启之后才可使用此形象卡`）

### 30.4 如果还想让地图上有翅膀

只剩两条路，都得先解决「翅膀面板被关」这件事：

1. **本地服把 `116 03` 放行**，让客户端翅膀窗口能打开。
