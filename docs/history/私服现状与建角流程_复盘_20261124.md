> 用途：给外部（ChatGPT）通读的技术底稿。目标不是"能进游戏"，而是**做一个和"他的服"一样的私服**：
> 新玩家自己注册、起名字、选男女、创建角色，登录后读到自己的角色数据，再逐步补齐任务/战斗/背包/装备/宠物/锻造/VIP/商城/活动/邮件/排行榜/多人同屏/世界BOSS。
>
> 所有结论分三类标注：**【实证】**＝抓包或反汇编直接看到；**【推断】**＝多个证据支持但未直接验证；**【待验】**＝未验证。

## 0. 一句话结论

登录、任务、战斗、背包、装备、锻造、VIP、多开隔离这些**已经跑通**，但**身份体系是假的**：
服务端不管谁来登录，都直接把一份默认角色/快照丢过去，没有真正的"注册 → 建角 → 存档"链路。
这正是"宠物面板空、属性面板不动、初始等级不对、一打怪闪退"一系列怪象的总根。
当前正在补的就是这一块：**客户端确实有独立的建角场景（CreateRoleScene），并且建角请求已经定位到 native 函数与命令号**。

### 4.2 native 层证据 【实证】

`so/libgame.so` 是 **Thumb-2 + GCC PIC**，字符串引用是 `ldr rX,[pc,#imm]` + `add rX,pc` 两段式，
直接搜绝对地址永远 0 hit（这是之前卡住的真正原因）。为此写了 `so/xref_pc.py`。

定位结果：

| 地址 | 含义 |
|---|---|
| `0x2eed06` | 引用 `assets/layout/create_role.xml` → CreateRoleScene 初始化 |
| `0x2ee870` | 建角场景按钮回调分发器（r1=0 返回 / 1 创建 / 2 随机） |
| `0x2ee8e8` | 引用 `name_outside_law`（昵称含非法字符的提示） |
| `0x2ee926` | 校验通过后的分支，调用建角发包 |
| `0x2ed608` | **建角请求构造函数**（r1=昵称串，r2=性别） |
| `0x2ed164` | **通用发包封装**（内部日志格式 `call cmd = %d, seq = %d`） |
| `0x2ef92a` | 引用 `please enter your name`（登录场景"无角色"提示） |
| `0x2f00e6` | 引用 `login_error_4`（登录错误分支） |

`0x2ee870` 反汇编（节选，说明校验逻辑）：

```asm
002ee88a  cmp  r1, #1                 ; 点的是「创建」
002ee88e  ldr.w r0, [r0, #0xf8]       ; 取 inputbox
002ee896  bl   0x482aec               ; 取文本
002ee89a  cmp  r0, #0xb               ; 长度 > 11 ?
002ee89c  ble  0x2ee8b2
002ee89e  ...  0x507e68               ; 超长 → 弹提示
002ee8b2  ...
002ee8ba  bl   0x4d6cd4               ; 合法性检查（敏感词/非法字符）
002ee8de  cmp  r0, #0
002ee8e0  bne  0x2ee926               ; 通过 → 发包
002ee8e2  ...  name_outside_law       ; 不通过 → 提示
```

`0x2ed608` 反汇编（节选）：

```asm
002ed608  push.w {r4,r5,r6,r7,r8,lr}
002ed60c  mov   r7, r2                ; r7 = 性别
002ed618  mov   r6, r1                ; r6 = 昵称
002ed62a  ldr   r3,[pc,#0xc4] ; ldr r3,[r4,r3] ; adds r3,#0xc
002ed630  str   r3,[sp,#0x24]         ; payload[0] = 全局消息体 + 0xc（昵称缓冲）
002ed644  add   r0, sp, #0x24
002ed646  mov   r1, r6
002ed648  blx   0x678724              ; 把昵称写进消息体
002ed64c  str   r7, [sp,#0x28]        ; payload[4] = 性别
002ed64e  bl    0x41d6fc              ; 取会话
002ed678  movs  r1, #0x14             ; ★ cmd = 20
002ed686  mov   r0, r6(session)
002ed68c  bl    0x2ed164              ; 发包
```

### 4.3 由此得到的建角请求形态 【推断】

```
C->S cmd = 20
payload ≈ { 昵称(定长/变长字符串), 性别(u32 或 u8) }
```

`0x2ed164` 里唯一的格式化日志是 `call cmd = %d, seq = %d`，r1 就是 cmd，所以 **cmd=20 可信度较高**。
但 `20` 是偶数，而本项目大量请求是奇数（17/145/146/149/211/115…）——**这条偶数规则在这游戏不成立**
（抓包里 4/22/46/82/90/116 都是偶数请求），所以不构成反证。

**目前缺的最后一环：真服新建账号的建角包原文。**
现有 `relay.log` 里只有老账号 1784366 的登录记录，没有一次"新账号 → 输入昵称 → 选男女 → 创建"的过程，
所以 cmd=20 的 payload 精确字节、以及服务端应答 cmd=21 的结构，**都还没有实证**。

## 5. 协议基础规范（已固化）

### 5.1 帧格式

```
[u16 total_len][u16 cmd][u32 seq][payload]
pack(cmd, seq, payload) = struct.pack(">HHI", 6+len(payload), cmd, seq) + payload
```

整帧遍历：`end = i + total + 2`（total 字段只算了 cmd+seq+payload）。

### 5.2 方向与 seq

- `seq=0` 一般是服务端主动推送；
- 请求/应答常用 `cmd` / `cmd+1` 配对，但**不是全局规律**（17 是双向同号）；
- 回放匹配必须写 `cmd in (cmd, cmd+1)`，只认 `cmd+1` 会丢登录响应 → 5 秒超时 → "网络连接失败"。

### 5.3 变长整数（venc）

```python
>=0x10000 → b"\xce" + u32BE
>=0x100   → b"\xcd" + u16BE
>=0x80    → b"\xcc" + u8
否则       → 单字节
```

### 5.4 已确认/在用的命令号

## 6. 已踩过的坑（不要重复）

1. **服务端对未注册 cmd 必须静默丢弃，绝不能回 `cmd=1`。**
   实测客户端收到 `cmd=1` 后 30ms 内 SIGABRT，无 Fatal、无 tombstone，看起来像"缺数据空指针"，实际是提示包打死的。
2. **心跳 4、位置 115 不要回**（客户端没注册 handler）。
3. **应答长度是硬约束**：211→212 回 1 字节必崩，回 22 字节（`00`+任务ID+17×`00`）才过。猜结构先给足填充，再看行为。
4. **证书只能用 `patch/exact.pem`**（md5 `b7b14333da8c59f084e5f4166d670ce0`），它是改包 APK 的 DEX 内嵌信任根；`srv.pem` 用错直接 TLS 失败。
5. **服务端必须受管后台跑**，`nohup &` 会被回收。
6. **判断崩溃真假看信号**：`Zygote: exited due to signal (6)` 才是 native 崩，`exited cleanly (0)` 是客户端自己退。
7. **relay.log 的 hex 字段最多 160 字符（80 字节）**，超长包在日志里是截断的；从日志抽数据必须校验"声明 len == hex 长度"，残包下发会闪退。
8. **存档必须过 `authed` 闸门**：未登录的半开连接只要碰了 `set_quest()` 就会用默认值覆盖主号存档。
   （2026-11-24 01:43 实测：Lv45 被冲成全默认的 Lv10/cls6/3件背包/任务400201。
   本轮又复现了一次：02:08 的 `player_state.json` 变成 405 字节的默认态，已从 `backups/player_state_20261124_015054.json` 恢复回 Lv45。）
   **说明闸门还不够，还要查是谁在 `authed=True` 但角色是默认态时写的盘。**
9. **不要"纠正"游戏设定**：例如系统发放的宠物就是"快照"，不等于做任务真的获得。
10. **sample < 100 的分类不要下结论**（统计上会被噪音翻转）。

## 7. 当前卡点（需要外部视角的地方）

### 卡点 1：cmd=20 的 payload 精确结构

已知：`{昵称, 性别}`，性别由 r7 直接 `str` 进 payload+4（说明 payload 至少 8 字节，且昵称区占 4 字节以内？还是 payload 是"指针 + 值"两段式？）。
**疑点**：`0x2ed630` 把 `全局消息体+0xc` 的**指针**存进 payload，再 `blx 0x678724` 写昵称——
这更像"消息体是全局单例，payload 只带指针/引用"，而不是序列化后的字节流。
如果真是这样，cmd=20 的实际线上字节可能只是 `[u8 性别]`，昵称在**连接建立时**或**登录包里**已经带过。
→ 需要一次真服建角抓包来定论。

### 卡点 2：服务端如何告诉客户端"这个账号没有角色，去建角"

`0x2ef92a` 的 `please enter your name` 和 `login_error_4` 分支说明客户端有"无角色"处理路径，
但 cmd=17 应答里哪个字段代表"无角色"，目前只能靠试。
→ 也需要真服样本（新账号登录时应答长什么样）。

### 卡点 3：新账号的账号本体怎么创建

登录包 `... a7 "1784366" da 002b <43B token>` 带 token，说明是账号+密码换 token。
真服是否"首次登录即自动注册"，还是另有注册协议（cmd=1x），未验证。

### 卡点 4：默认角色仍在污染存档

闸门只挡了"未登录"，挡不住"登录了但角色是默认值"。
建议改成：`Player` 增加 `loaded` 标志，只有 `load_state()` 真正读过盘的角色才允许 `save_state()`。
