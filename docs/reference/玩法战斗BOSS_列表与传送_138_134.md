## 三、结论（写代码要用的）

1. **传送是服务端驱动的**，客户端只发 7 字节 134，位置由 129 决定，客户端不校验落点合法性。
2. **落点是逐个 boss 配的「挑战位」**，不是统一偏移：
   - 九尾狐 boss (21,0) → 落 (22,0)，右一格
   - 玄蜂 boss (42,1) → 落 (41,1)，左一格
   - 灭蒙 boss (25,1) → 落 (24,1)，左一格
   - 天鹿 boss (25,1) → 落 (26,1)，右一格
   - 白泽（当时不在图上）→ 落 (37,0)

   灭蒙和天鹿**同为 (25,1)**，落点却一个左一个右 —— 落点没有任何可推的规律，是服务端按 boss 逐条配的。本地必须按入口写死坐标，客户端不校验合法性。
3. **113 反映的是当时真实刷怪状态**，134 不会强行刷怪。boss 在图上时 113 带该刷怪点（样本 A/E），不在时就是空刷怪表（样本 B/C/D）。
   **2026-11-28 00:55 现场确认**：102 的九尾狐/玄蜂、105 的白泽是**被别的玩家打掉了**，不是本地早期猜的「进挑战态把 NPC 摘掉」；110 的灭蒙当时没人打，所以四个点都在。本地按自己的存活状态生成 113 即可，击杀后照旧发 121。
4. **117 是「条数 + 定长记录」**，不是定长包：`[n][n × 6B]`，长度 `1 + 6n`。四份样本全部吻合：
   - `00` → n=0（样本 A，1B）
   - `01 0b2206000000` → n=1，记录 `0b 22 06 00 00 00`（样本 B/C，7B）
   - `02 162302004000 | 0f0b00000000` → n=2（样本 D，13B）
   - 登录场景：`01 163002004000` → n=1（7B）

   记录前两字节像坐标（(11,34)、(22,35)、(15,11)），后四字节含类型位（`02004000` / `06000000` / `00000000`）。用途未定，但样本 A（n=0）之后客户端能正常发 145 开打，所以本地维持 `117(00)` 是安全下限；要还原传送点/跳点，就按场景发对应的 n 条记录。
   **注意 117 与刷怪数量无关**：样本 E 四个 boss 全在图上，117 仍是 n=0；而同一场景 104 登录时是 n=1、传送过来是 n=0 —— 不是纯场景常量，语义未定，本地发 `00` 即可。
5. **本地实现顺序**：`138` 回放 224B → `134` 查表 → `129` + `113`（按本地刷怪表生成，带 boss）+ `117(00)` + `ACK 2` → 更新 `cur().scene/x/y`。九尾狐 / 玄蜂 / 灭蒙 三条有逐字节样本，其余按 138 的场景字段映射，落点按「boss 左/右一格」推定并在日志标「推断」。

6. **场景 110 的刷怪点坐标暴露了本地公式的一个 1 格偏差**。真服四个点 `(12,0) (25,1) (38,0) (51,1)`，本地 `build_113` 的 `63*(i+1)//(n+1)` 算出 `12, 25, 37, 50` —— 第 3、4 个各差 1 格。真服规律更像 `起点=floor(63/(n+1))，步长=ceil(63/(n+1))`：n=4 → 12 步长 13 → 12/25/38/51 ✓；n=3 → 15 步长 16 → 15/31/47 ✓；n=2 → 21 步长 21 → 21/42 ✓。改 `build_113` 时按这个换。
