## 二、抓包方法（可复现）

不改 APK、不重签、不用 frida。原理是把客户端的出站流量引到本机代理：

```
模拟器内:
  iptables -t nat -A OUTPUT -p tcp -d 124.223.56.189 \
      -j DNAT --to-destination 192.168.0.111
```

- 宿主 IP 用 `192.168.0.111`，**不能用 172.16.1.1**（那是虚拟网关，宿主机上没有该地址，包会被丢弃，表现为 DNAT 计数增长但代理收不到）。
- 模拟器网段：`172.16.1.0/24`，wlan0 = 172.16.1.4，网关 172.16.1.1。
- 代理按首字节分流：`0x16` → TLS 透传（那是 HTTPS 的 `/auth` 登录接口）；其余 → 明文游戏协议并 dump。
- TLS 透传保证客户端校验的仍是真服务器证书（CN=124.223.56.189），登录不受影响。

> 踩坑：hosts 劫持对**IP 字面量无效**。客户端从 `server-list.xml` 读到的 `ip="124.223.56.189"` 是 IP，不走 DNS，所以必须用 iptables DNAT，改 hosts 没用。

## 三、协议规范（实测确认）

### 3.1 包结构

```
+--------+--------+------------+------------------+
| u16 BE | u16 BE |  u32 BE    |                  |
|  len   |  cmd   |    seq     |     payload      |
+--------+--------+------------+------------------+
   2B       2B        4B          len-6 字节
```

- `len` = **6 + payload 长度**（即不含自身 2 字节）
- 全部字段**大端序**
- 单包上限实测 > 158 字节正常工作

### 3.2 cmd 方向规则

**奇数 cmd = 客户端请求，偶数 cmd = 服务端响应（响应 cmd = 请求 cmd + 1）**

实测 21 组配对全部成立：

```
177 → 178    190 → 191    193 → 194    209 → 210
305 → 306    529 → 530    657 → 658    689 → 690
881 → 882    981 → 982   1265 → 1266  1345 → 1346
1409 → 1410 1505 → 1506  1921 → 1922  2113 → 2114
2115 → 2116
```

### 3.3 seq 规则

- 客户端 seq 从 2 开始递增（1 可能被登录占用）
- 服务端响应回**同一个 seq**
- `seq=0` 表示**服务端主动推送**，客户端不需要应答

### 3.4 登录握手（cmd 0x11 = 17）

**C→S**（len=64, seq=2）：

```
01                    # 标志位
cc 97 02 a7           # 4 字节（时间戳/随机数，待确认）
a7 "1784366"          # 昵称，前缀 0xa7 疑为长度标志（0xa0|7）
da 00 2b <43字符>      # 0xda 标志 + u16 BE 长度 43 + token
```

其中的 43 字符串就是 `/auth` 返回的 base64url token：

```
+pqSFlWNLHftkm_DkW8ZLMIzsW4LoS3IB4_Ts1KLg8YM
```

**S→C**（len=158, seq=2）：带回完整角色数据

```
0c a7 "1784366" a6 "萌新"      # 账号 + 角色名（UTF-8 中文，前缀 0xa6=长度6）
01 06 01 30
1f 00 65 10 07 00 ...          # 属性块：等级 0x47(71)、坐标、HP/MP 等
47 00 00 00 00 01 00 00 00 cd 02 f8
30 1f 07 0d 00 1e 00 1e 00 05 28 ...
```

`0xa0|长度` 的字符串编码方式在后续包中反复出现（`0xa6`=6字节、`0xa7`=7字节、`0xa0`=0字节），可视为该协议私有 TLV 的一种。

### 3.5 已识别的 cmd

| cmd | 方向 | payload | 含义 |
|---|---|---|---|
| 1 (0x01) | S→C | 提示文本 | 通用提示/错误回复。`payload = [u16 模板id][UTF-8 文本]`，seq 与触发它的请求一致；实测 8 次均为「本服尚未恢复此功能」 |
| 4 (0x04) | C→S | 5B `ce 6b 02 61 XX` | 高频同步/心跳，末字节每次 +0x0a |
| 0x11 (17) | 双向 | 见上 | 登录握手 |
| 0x1c/0x1d (28/29) | S→C 推送 | 属性块 | 角色属性下发 |
| 113 (0x71) | S→C 推送 | 34B | 场景/玩家列表（含 `ce 00 01 b1 fd 0f` 结构） |
| 116/117 (0x74/0x75) | C→S | 1B | 简单指令 |
| 0xb2 (178) | 双向 | 9B / 23B | 背包或物品变更 |
| 0xb6 (182) | 双向 | 2B `00 01` | 开关类操作 |
| 0xd3 (211) | 双向 | 5~7B | 客户端位置上报（点击移动） |
| 0x7f01 (32513) | S→C | 3B | 系统消息 |

其余 30+ 个 cmd 目前只有「请求 payload=0 / 响应 payload=N」的空壳，需要继续在游戏里触发对应功能才能填充语义。

## 五、自建服务端 L1 验证（已实测）

### 5.1 做法

写了一个 `legacy/local_server.py`，接管 9000 端口，按首字节分流：

- `0x16` → TLS，**透传给真服务器**（`/auth` 登录接口照常走，证书仍是真服的）
- 其他 → 明文游戏协议，**本地应答**

客户端不用改、不用重签。只需 `DNAT` 把 `124.223.56.189:9000` 指到本机。

响应数据来自抓包提取的模板（`templates.json`，62 条），按 cmd 回放。

### 5.2 实测结果

客户端完整走通：

```
c001 TLS -> 透传给真服 /auth            登录成功
c002 <- cmd=17  payload=58  (账号+token)  ← 客户端发登录握手
c002 -> 登录响应 152 字节                  ← 本地服回放真实角色数据
c002 <- cmd=981/177/657/1384/529/536/956/881/849/1125/1134/1282/1409/
        1345/193/190/1921/87/2113/2115/305/90/1505/22/502/209/849/689/
        1154/663/32513                   ← 31 个初始化请求全部应答
c002 异常 ConnectionResetError            ← 客户端主动断开
```

**31 个初始化请求全部获得响应，客户端全部接受**，说明协议层完全正确。

### 5.3 卡在哪

最后崩在 `SIGABRT (signal 6)`：

```
11:39:03.366  enter native_bridge2_getTrampoline
              Java_com_aiyou_mhsj_JniHelp_nativeGetFileOffsetAndSize
11:39:03.411  Process 4890 exited due to signal (6)
```

客户端初始化到最后一步要**按偏移读本地资源文件**（`mhsj.mpkg` 内的条目），找不到目标条目就直接 abort。

这不是协议问题，是**资源索引不匹配**：本地服返回的角色/场景数据引用了某些资源，而模拟器里装的这版客户端资源里没有。

修法（下一步）：
1. 把下载到的 114.6MB `mhsj_res.zip` 覆盖进客户端资源目录
2. 或让本地服用「空场景、空角色列表」的最小数据响应，避免引用不存在的资源

## 六、自建服务端：做到哪一步需要多少工作

### 6.1 已验证可行的路径

```
客户端 → server-list.xml（可改指向）→ 你的 9000 端口
      → cmd 0x11 登录握手（格式已完全掌握）
      → 后续 cmd 按需应答
```

因为：
- `server-list.xml` 只返回 `ip` / `port`，改一处即可把客户端指向你的服务器
- 协议是明文，不需要处理加密
- 包头 + cmd 规则 + seq 机制已完全掌握

### 6.2 分层工作量（基于实测重新估算）

| 层级 | 目标 | 关键 cmd | 工作量 |
|---|---|---|---|
| L1 | 客户端连上你的服，过登录 | 0x11 一组 | ✅ 已完成 |
| L2 | 进主城，看到角色 | 0x11 + 角色属性(0x1c/0x1d) + 场景(0x71) | ✅ 已完成（2026-11-22） |
| L3 | 走路、NPC 对话、基础交互 | 0x04 + 0xd3 + 若干 | **2–3 周** |
| L4 | 任务、战斗、背包、商城 | 数十个 cmd | **2–4 个月** |
| L5 | 全部系统可玩 | 全部 | 半年以上 |

### 6.3 一个客观参照

**这个私服是「部分实现」，不是全残**。

抓包里「本服尚未恢复此功能」只出现在 **8 个请求**上，全部可枚举：

| 请求 cmd | 次数 |
|---|---|
| 1384 (0x568) | 1 |
| 1125 (0x465) | 1 |
| 1134 (0x46e) | 1 |
| 22 (0x016) | 1 |
| 663 (0x297) | 1 |
| 116 (0x074) | 3 |

其余 30+ 个请求都有正常响应（属性、场景、背包等）。

**修正**：早期版本把这一条写成「点任务即提示未恢复 → 任务系统没跑起来」，过头了。
用户实机验证**任务可以正常提交**，说明这 8 个 cmd 对应的是另外几个没实现的子系统（具体是哪几个，需要一次带标注的抓包才能定谳）。
也就是说：服主的完成度比我上一版估计的高，你想「做得比他完整」的门槛也相应更高。
